- TG：整張交易訂單／訂單群組。本例的總金額是 1,497 元。

Independent 是同一張 TS 的商品先合併並以此為單位計算(不是每個 SKU 各算一次)。因此，若 Engine 收得到這兩張 TS 的 GroupKey，計算會是 floor(998 × 10%) + floor(499 × 10%) = 99 + 49 = 148 點。Merged 則把整張 TG 合起來算：floor(1,497 × 10%) = 149 點。

兩種模式都先用符合活動條件的總金額判斷門檻、選出回饋比例。

差別在於後續計算和無條件捨去的單位，Merged 以 TG 算一次，而 Independent 以 TS 分別計算、分別捨去。因此 TS 越多、各 TS 算出的小數越多，Independent 最終的點數通常越少，且通常不會高於 Merged


那為什麼開頭的購物車仍顯示與 Merged 計算結果相同的 149 點？因為這條預估鏈路送進 Engine 的 GroupKey 都是 null。規則雖然選了 Independent，Engine 在這裡仍只分得出一組而無法依據 TS 各自計算

<div class="tg-flow">

剛才那筆購物車，整張 TG 合起來算是 149 點；假設依兩張 TS 分開算，則是 148 點。只差一點，問題卻不在算術，而在活動規則究竟把誰當成「一組」

決定計算方式的是 `PointCalculateType`。本文討論的主要是這兩種比例回饋活動

- `RewardReachPriceWithRatePoint`
- `RewardReachPriceWithRatePoint2`


程式裡只有兩個選項

```csharp
public enum RewardPointCalculateType
{
    // TG
    Merged = 1,

    // TS
    Independent = 2
}
```

`Merged` 是整張 TG 合起來算；`Independent` 是依 `Product.GroupKey` 分組算

其中，`RewardReachPriceWithRatePoint2` 預設選的是 `Merged`：

```csharp
public RewardPointCalculateType PointCalculateType { get; set; }
    = RewardPointCalculateType.Merged;
```

<!-- tab 門檻先看總額，點數才看分組 -->

<div class="tg-flow">

前面假設商品 A、B 屬於第一張 TS，金額 998 元；商品 C 屬於第二張 TS，金額 499 元。活動規則是「滿 1,000 元回饋 10%」

998 元離門檻只差 2 元，難道第一張 TS 要在門口被攔下來？先別急。Engine 判斷門檻時，看的不是各張 TS，而是**所有符合活動商品的總額**：`998 + 499 = 1,497` 元。因此這筆交易達到門檻，選用 10% 的回饋比例

程式的順序也是如此

```csharp
var items = this.GetMatchedProductScopeItems(context)
    .OrderBy(x => x.SalePrice)
    .ThenByDescending(x => x.Id)
    .ToArray();

var totalPrice = items.Sum(x => x.SalePrice);

var priceRateAndPointPair = threshold.ReachPriceRatePointPairs
    .Where(x => x.ReachPrice <= totalPrice)
    .OrderByDescending(x => x.ReachPrice)
    .FirstOrDefault();
```

`GetMatchedProductScopeItems` 先找出符合活動範圍的商品，`Sum` 算出總額，再由 `ReachPriceRatePointPairs` 選出這個總額適用的門檻與比例。**這幾步不會因為選了 `Independent`，就改成每張 TS 各闖一次門檻。**

到這裡，門檻和 10% 都已經決定；接下來才輪到 `PointCalculateType` 決定：要把 1,497 元合起來算點數，還是依 `GroupKey` 分組後各算各的。

<!-- tab Merged：整張 TG 算一次 -->

<div class="tg-flow">

門檻已經過了，比例也選好了 10%。`Merged` 接下來做的事很乾脆：先把符合活動的商品金額全部合起來，算完點數才捨去小數

程式只有這一行：

```csharp
var points = (totalPrice * priceRateAndPointPair.Rate).Fix(0);
```

放回開頭的例子，第一張 TS 是 998 元，第二張 TS 是 499 元。`Merged` 不在這裡分兩次算，而是先合成 1,497 元，乘上 10% 得 149.7 點，最後取整為 149 點。


`Fix(0)` 的核心實作如下。對這筆正數金額，它會把小數向下取整：

```csharp
var output = Math.Floor(input * power) / power;
```

所以 `Merged` 的關鍵是**整張 TG 算一次、捨一次**；這 149 點寫成一筆 `PromotionRecord`，其 `Group` 標記為 `Merged`。

<!-- tab Independent：每張 TS 各算一次 -->

<div class="tg-flow">

`Independent` 換了一種排隊方式：先看 `Product.GroupKey`，同一個 key 的商品站在同一組，再讓每組各算各的點數。假設開頭的三件商品有正確的 TS 識別值，送進 Engine 時會像這樣：

| 商品 | 金額 | `Product.GroupKey`（示意） |
| --- | ---: | --- |
| A | 499 元 | `TS1` |
| B | 499 元 | `TS1` |
| C | 499 元 | `TS2` |

A、B 雖是兩件商品，卻同屬 `TS1`，所以要先合成 998 元；C 屬於 `TS2`，是另一組。程式正是照這個順序處理：

```csharp
decimal points = items
    .GroupBy(g => g.Product.GroupKey)
    .Sum(x =>
        x.Sum(g => g.SalePrice * priceRateAndPointPair.Rate).Fix(0));
```

`GroupBy` 先把商品分組；內層的 `Sum` 算出每組套用 10% 後的點數，接著每組各做一次 `Fix(0)`；最外層的 `Sum` 才把 99 點與 49 點加成 148 點。


同樣是 1,497 元、同樣選 10%，`Merged` 得到 149 點，這裡得到 148 點。差的 1 點來自**每張 TS 都先捨去自己的小數**，不是重新判斷門檻，也不是每個 SKU 各算一次。

但 `GroupBy` 只認 `GroupKey`，不會猜商品應該屬於哪張 TS。若三件商品的 key 全是 `null`，它們就會排成同一組。這正是目前購物車預估鏈路的情況：規則雖選了 `Independent`，結果仍是 149 點；`PromotionRecord.Group` 標記為 `Independent`，也不代表資料真的被分成多張 TS。

另外，若各組加總後的點數小於 0，程式會將結果調整為 0：

```csharp
if (points < decimal.Zero)
{
    points = 0;
}
```

一般化來看，`Merged` 先合併各 TS 金額再取整；`Independent` 先讓各 TS 分別取整，再把點數加總。


在各組金額非負、沒有其他點數限制的情況下，`Independent` 的結果小於或等於 `Merged`；有時會少點，也可能剛好相同。

## 實際走一遍：購物車兩列，計算時變三件

為了看清楚 `Qty` 怎麼轉成 Engine 的商品資料，這裡換一筆**總額同為 1,497 元**的示意購物車。商品 X 買兩件、商品 Y 買一件，每件 499 元；都符合「滿 1,000 元回饋 10%」活動，沒有其他折扣。以下 ID 與資料只是範例，並非實際 API 紀錄。

| Cart 快取中的商品列 | `CartId` | `SkuId` | `Qty` | 每件價格 |
|---|---:|---:|---:|---:|
| 商品 X | 101 | 501 | 2 | 499 元 |
| 商品 Y | 102 | 502 | 1 | 499 元 |

**① Shopping → Cart：只用識別碼要求重算。**Shopping 建立 `CartCalculateRequest`，POST 到 Cart 的 `/api/carts/calculate`：

```text
CartUniqueKey = "cart-demo-123"
```

此時的 request **沒有**上表的商品列。Cart 的 `LoadCacheCartDataProcessor` 使用識別碼，連同請求環境中的商店與會員資訊，從快取取出含 X、Y 的完整 `CartEntity`。Shopping 傳來的像是領車的號碼牌，商品明細還在 Cart 快取裡。

**② Cart → FrontendAPI：Cart 才開始組完整促購 request。**`ArrangePromotionPayloadAsync` 從 `CartEntity.SalepageGroupList` 取得商品；`GetPromotionRequestSkuListAsync` 轉成下列 `SalepageSkuList`。`PromotionHttpClient.Calculate` 將包含這份清單的 `CalculateRequestEntity` 以 JSON POST 到 `/api/cart-calculate`。

```text
SalepageSkuList[0]：CartId=101, SkuId=501, Qty=2, Price=499
SalepageSkuList[1]：CartId=102, SkuId=502, Qty=1, Price=499
```

同一個 request 還有 `Shop`、`User`、`Channel`、`Payment`、`Shipping`、`CouponList` 等資料，這裡先聚焦商品。關鍵是：這份商品清單的型別**沒有 `GroupKey` 欄位**。`Merged`／`Independent` 也不是由這兩列商品指定，而是 FrontendAPI 載入活動規則後才知道。

**③ FrontendAPI → Engine：`Qty=2` 的 X 被攤成兩件。**`CreateProcessContextAsync` 的 `for (i < Qty)` 產生三筆 `SalepageSkuItemEntity`；`CreateShoppingCartContext` 再為每筆建立一個 `ProductItem`。兩列購物車商品，到這裡變成三筆計算用商品。

| Y 的第 1 件 | 3 | 102 | 502 | 499 | `null` |

X 的兩件雖有相同的 `CartId`、`SkuId`，仍各自成為一筆計算用商品；三件的 `GroupKey` 都是 `null`。Engine 不會拿 `CartId`、`SkuId` 或 `Index` 代替 `GroupKey` 分組。

**④ Engine → Cart → Shopping：算完再把點數送回去。**三件商品的 `SalePrice` 合計 1,497 元，達到 1,000 元門檻，選用 10%。`Merged` 算出 `floor(1,497 × 10%) = 149` 點；即使活動規則是 `Independent`，目前這條路徑的三個 `GroupKey` 都是 `null`，仍只形成一組，也算出 149 點。Engine 將 `PromotionRecord.Point` 回傳 Cart；Cart 寫入 `PromotionInfoList[].Points`、保存快取，再把結果回給 Shopping。

## 一件商品對應一個 `ProductItem`，不代表一件一張 TS

剛才 X 的 `Qty=2`，在 `CreateProcessContextAsync` 的迴圈裡變成兩筆單件商品；Y 的 `Qty=1` 變成一筆。每筆都有自己的 `Index`，`BaseProcessGroup.CreateShoppingCartContext` 再逐件建立 `ProductItem` 並呼叫 `Purchase()`。所以 `Qty` 的**每一件**，確實各有一個計算用的 `ProductItem`。

可是 `ProductItem` 是「一件商品」的資料，不是「一張 TS」的證明。`Independent` 真正拿來分組的是 `Product.GroupKey`：相同 key 合併，不同 key 分開。Engine 不會從 `SkuId`、`CartId` 或 `Index` 猜出 TS 單號；在這條購物車路徑，三件商品的 key 都維持 `null`，最後自然只分得出**一組**。

## 同樣三件商品，分組不同就有不同點數

把三件各 499 元、都符合活動的商品排在一起看。假設滿 1,000 元回饋 10%，沒有其他折扣與點數上限；四種算法都先以 1,497 元總額通過門檻並選用 10%。

| 活動設定與 `GroupKey` | Engine 看見的計算組 | 點數 |
| --- | --- | ---: |
| `Merged` | 整張 TG 一組 | `floor(1,497 × 10%) = 149` |
| `Independent`，三件都是 `null`（**目前購物車**） | 仍是一組 | `floor(1,497 × 10%) = 149` |
| `Independent`，前兩件 `TS1`、第三件 `TS2`（假設） | 兩組：998、499 元 | `99 + 49 = 148` |
| `Independent`，三件各有不同 key（假設） | 三組：各 499 元 | `49 + 49 + 49 = 147` |

表中最容易看漏的是第二列：`PromotionRecord.Group` 即使標示 `Independent`，也只能說程式走了這個分支，**不能據此認定它真的分出了多張 TS**。是否分組，還得看呼叫方有沒有提供不同的 `GroupKey`。

## `basket-calculate` 也會填 `GroupKey` 嗎？

`POST /api/basket-calculate` 依 `PromotionSourceType` 選擇 BasketGroup，並共用 `CreateProcessContextAsync`。一般 `PromotionBasketGroup` 使用 `BaseProcessGroup.CreateShoppingCartContext`；`CustomRuleBasketGroup` 也先呼叫這個 base 方法，另外設定計算日期。因此，若 basket 計算載入 `Independent` 比例回饋規則，這條商品建立路徑目前也**沒有填入** TS `GroupKey`。

FrontendAPI 確實還有其他流程會填 `GroupKey`，但填的是各自業務需要的分組值：換價流程使用組合商品組號或 `CartExtendInfoItemGroup`；點數**折抵**服務則結合 SKU 與選項資訊，計算折抵上限。這些流程各自建立 Engine 商品資料，不會自動替回饋活動的 `cart-calculate` 或 `basket-calculate` 補上 TS 識別值。
