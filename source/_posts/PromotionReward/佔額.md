<div class="quota-lead"><p>訂單符合回饋活動後，系統先向 PCPS 保留一筆額度。線上訂單要等付款結果，才能決定繼續給獎或返還；線下訂單則在回饋流程中完成佔額</p></div>

「佔額」是回饋活動在 **PromoCodePool Service（PCPS）** 的 Group 中，先替符合條件的訂單會員分派並兌換一筆 Code，使該筆回饋占用活動限額。這是配額操作，**不是給點或給券**。Promotion Worker 另外在 DynamoDB（下稱 DDB）存回饋主單及子單狀態，藉此決定後續是否能回饋、取消及稽核



本專案支援三種相關活動類型：`RewardReachPriceWithPoint2`、`RewardReachPriceWithRatePoint2`、`RewardReachPriceWithCoupon`，分派器、Job 的 `IsQuotaPromotion` 使用由 `GroupCode` 判斷

  find --> reverse["PCPS reverse-redeemed-and-dispatched"]

  record -->|"Unmatch、MatchWithoutQuota、Cancel"| skip["略過返還"]
  record -->|"查無紀錄"| error
  record -->|"其他狀態"| error["拋出異常"]
{% endmermaid %}
</div><figcaption><code>OrderFailed</code> 在分派器內直接處理返還。查不到紀錄或遇到未預期狀態會報錯。</figcaption></figure>



`OrderFailed` 在同一個 Dispatcher 內直接走返還流程，不會建立上述佔額 NMQ Task。只有 DDB 主單為 `Occupy` 才以 `GroupCode + TG` 查 PCPS 的 `CodeId`，呼叫 `reverse-redeemed-and-dispatched`，成功後更新 DDB 為 `Cancel`；給券活動還會更新取消券數量。這裡的 `reverse-redeemed` 是**返還已佔額度**，與 `OrderPlaced` 後 Job 執行的 `dispatch-and-redeem` 是相反操作

`OrderCreated` 的後續回饋分派與 `Occupy → WaitToReward` 轉換，見「何時佔額：線上與線下」分頁；它不是 `PromotionRewardOccupyDispatcherJob` 的分支

PCPS（Promo Code Pool Service）以 **Group** 保存活動的佔額規則，以 **Code** 表示一次已分派的額度。Promotion Web API 建立活動時負責建立並啟用 Group；Worker 在訂單符合活動後，才對該 Group 呼叫 `dispatch-and-redeem`。建立群組得到的 `Id` 會寫成活動的 `PromotionEngine_GroupCode`，Worker 取得規則後則可從 Rule-Record 的 `GroupCode` 找到同一群組

**建立／更新 Group 的參數**

| PCPS 欄位 | Promotion Web API 傳入值 | 在回饋活動的意義 |
|---|---|---|
| `ModeType` | `Functional` | 用多少才產生多少 Code；不是先匯入整批代碼。 |
| `DispatchType` | `Random` | 搭配 `Functional` 時，依代碼產生規則即時產生 Code；此處的 `Random` 不是「隨機決定哪筆訂單中活動」。 |
| `Pattern` | `GUID` | 產生 Code 使用的格式設定。 |
| `Since` | 活動的 `StartDateTime` | 群組開始時間。 |
| `Until` | `DateTime.MaxValue` | 群組不隨活動的 `EndDateTime` 到期，讓活動結束後補處理舊訂單時仍可使用該群組；活動本身是否有效仍由活動時間與規則判斷。 |
| `LimitRuleSettings[].ActionType` | `Redeem` | 限額規則套用在兌換動作。 |
| `LimitRuleSettings[].LimitTarget` | `2` | PCPS 的會員限額維度；Web API 程式碼明註 `2` 代表會員。 |
| `LimitRuleSettings[].LimitRules[].Quota` | 活動的 `Quota` | 上述會員維度的兌換額度設定。`Quota <= 0` 時，建立群組方法不接受該設定。 |
| `CanRedeemDirectly` | `true` | 允許直接兌換；Worker 使用的 `dispatch-and-redeem` 會在同一次呼叫中分派並兌換 Code。 |

Web API 透過 `POST api/groups` 建立、`PATCH api/groups/{id}/enable` 啟用，更新時用 `PUT api/groups/{id}`

**建立 Group 實例。** 假設商店 `1001` 建立一檔回饋活動，活動期間為 **2025-05-01 00:00 至 2025-05-31 23:59（台灣時間）**，設定 `Quota=1`。Promotion Web API 會依活動資料組成下列 PCPS request。商店與活動設定是示意值；欄位及 `Until=DateTime.MaxValue` 對應 `PromoCodePoolService.BuildQuotaGroupRequestEntity` 的實際程式碼。

```csharp
// POST api/groups；此處以 C# 表示 Web API 組出的 request，非 HTTP 原始 JSON。
new GroupCreateOrUpdateRequestEntity
{
    ModeType = "Functional",
    DispatchType = "Random",
    Pattern = "GUID",
    Since = new DateTimeOffset(2025, 5, 1, 0, 0, 0, TimeSpan.FromHours(8)),
    Until = DateTime.MaxValue,
    LimitRuleSettings = new[]
    {
        new LimitRuleSettingEntity
        {
            ActionType = "Redeem",
            LimitTarget = 2, // 會員
            LimitRules = new[] { new LimitRuleEntity { Quota = 1 } }
        }
    },
    CanRedeemDirectly = true
};
```

建立成功後，Web API 取回 PCPS 回應的 `Id`，再呼叫 `PATCH api/groups/{id}/enable`。假設回傳 `Id=6f114aae-3391-4e0d-84cc-fdb3ed68e87a`，活動會把這個字串存成 `PromotionEngine_GroupCode`，後續訂單就用它指定要佔額的 Group。此 ID 僅為串連範例的示意值，程式碼沒有保證 Group ID 一定採用 GUID 格式。雖然活動在 5 月底結束，Group 的 `Until` 仍為 `DateTime.MaxValue`；訂單是否屬於活動期間，仍需按訂單時間與活動規則判斷。



**每筆訂單佔額的參數**

| 欄位 | Worker 傳入值與用途 |
|---|---|
| URL 的 `groupId` | 活動的 `GroupCode`，指定要佔用哪個 PCPS Group。 |
| `ReceiverId` | 會員 ID 的字串，指定接收這筆 Code 的會員。 |
| `Tags` | 空集合。Worker request model 說明 `Tags` 用來形成限額鍵、不能拿來查詢；此流程沒有額外傳入 Tag。 |
| `Labels` | 放訂單彙總碼 TG，作為可查詢註記。後續以 `GroupCode + TG` 呼叫 `get-by-label` 找出該訂單的 Code。該欄位的 model 註明長度上限為 180 bytes，且不得包含 `@` 或 `\|`。 |
| HTTP headers | `ny-market` 是市場、`ny-shop-id` 是商店 ID、`ny-source-type` 固定為 `PromotionReward`；Worker 佔額時的 `ny-user-id` 是會員 ID。Web API 建／改 Group 時的 `ny-user-id` 則來自操作使用者名稱。 |

線下訂單在查 DDB／PCPS 時使用 `CrmSalesOrderCodePrefix + CrmSalesOrderId` 作為訂單代碼。PCPS 回傳的單筆 `CodeId` 用於日後返還；HTTP 成功不等於佔額成功，Worker 還會確認回傳 `State=Redeemed`

**線上訂單佔額實例。** 沿用上面的 Group，假設會員 `2002` 在 **2025-05-12** 下了一筆線上訂單 `TG250512P00001`，`OrderPlaced` 佔額 Job 試算後確認 `IsMatch=true`。這個 TG 樣態取自專案測試資料；商店、會員及 Group ID 仍是示意值。Worker 會送出：

```http
POST api/groups/6f114aae-3391-4e0d-84cc-fdb3ed68e87a/dispatch-and-redeem
ny-market: TW
ny-shop-id: 1001
ny-source-type: PromotionReward
ny-user-id: 2002
Content-Type: application/json

{
  "receiverId": "2002",
  "tags": [],
  "labels": ["TG250512P00001"]
}
```

這裡的 URL 指向活動 Group，`receiverId` 指向會員，`labels` 把 Code 與 TG 關聯起來，`tags` 沒有額外值。若 PCPS 回傳 `State=Redeemed`，Worker 視為佔額成功，線上 DDB 主單記為 `Occupy`；之後可用相同 `GroupCode` 與 `Label=TG250512P00001` 呼叫 `get-by-label` 查回該 Code。

**線下訂單佔額實例。** 同一檔活動若也適用線下訂單，假設另一位會員 `2003` 的 `CrmSalesOrderId=987654321` 在活動期間符合回饋條件。線下回饋 Job 會把 CRM 訂單 ID 組成 `CrmSalesOrder:987654321`，將它當作 PCPS Label；`CrmSalesOrder:` 是 `OthersCrmSalesOrderPromotionRewardCalculateService.CrmSalesOrderCodePrefix` 的實際常數值。線下不會先等 `OrderPlaced` 佔額 Job，而是在回饋 Job 試算命中後送出：

```http
POST api/groups/6f114aae-3391-4e0d-84cc-fdb3ed68e87a/dispatch-and-redeem
ny-market: TW
ny-shop-id: 1001
ny-source-type: PromotionReward
ny-user-id: 2003
Content-Type: application/json

{
  "receiverId": "2003",
  "tags": [],
  "labels": ["CrmSalesOrder:987654321"]
}
```

線下查詢時也用該 Group ID 與 `Label=CrmSalesOrder:987654321` 呼叫 `get-by-label`。若 PCPS 回傳 `State=Redeemed`，線下 DDB 主單直接進入 `WaitToReward`；同一範例使用不同會員，是因為 Group 設定的 `Quota=1` 套用在會員限額維度。兩種訂單的 request 欄位與成功判斷都對應點數／券 Job 的 `ProcessOccupyQuotaAsync`

回饋活動的有效期和 PCPS 佔額群組的有效期是兩組設定。活動規則的 `Since`、`Until` 分別採用活動的 `StartDateTime`、`EndDateTime`，用來判斷訂單在下單當時是否符合活動時間。建立 PCPS 群組時，`Since` 同樣採用活動開始時間，但 `Until` 固定為 `DateTime.MaxValue`，沒有跟著活動結束時間到期。因此，活動已結束後，只要補跑流程仍能找到該活動與訂單，過去符合活動期間的訂單仍有機會在現在向 PCPS 佔額


| 情境 | 活動時間判斷 | PCPS 群組時間判斷 | 結果 |
|---|---|---|---|
| 現在補跑活動期間內的舊訂單 | 訂單時間落在活動開始與結束之間 | 群組的 `Until` 尚未到期 | 時間設定不會阻止佔額，仍須符合活動條件且有額度 |
| 現在處理活動開始前的訂單 | 訂單時間早於活動開始 | 即使群組已存在 | 訂單不符合活動時間，不應進入該活動佔額 |
| 現在提前處理未來活動的訂單 | 訂單時間可能落在未來活動期間 | 處理當下早於群組 `Since` | 依群組設定不應提前佔額；PCPS 的實際拒絕行為仍須以 PCPS 實作確認 |

<div class="quota-note"><p><strong>補跑的界線：</strong>Group 不隨活動結束而過期，讓舊訂單仍有機會佔額；一般 Worker 的候選活動查詢範圍仍會影響能否補跑。</p></div>

建立活動時，backend API 只對支援佔額的回饋類型且 `Quota > 0` 的活動建立並啟用 PCPS 群組，取得 `GroupId` 後寫入 `PromotionEngine_GroupCode`。`Quota = 0` 代表不建立佔額群組。活動開始後，更新流程會直接跳過佔額設定變更

這個時間設定解決的是 PCPS 群組過期問題，不保證任意久以前的活動都能由一般 Worker 分派器找出。目前該分派器的候選活動查詢從現在往前七天開始，再用訂單時間過濾；超過查詢範圍的補跑仍需檢查實際入口



## 佔額更新

活動尚未開始且有佔額設定時，backend API 可以更新群組的額度與開始時間；活動開始後，佔額設定更新流程會直接返回。

## 資料表

`PromotionEngine_GroupCode` 保存 PCPS 回傳的 Group ID，供 Worker 從活動規則取得後佔額。

## 線上訂單（ECom）

1. `OrderPlaced` 到達佔額分派器。它按**訂單時間**選出有效的三類回饋活動，保留有 `GroupCode` 的活動；點數活動還需 `ExtendInfo` 有值。每檔活動各建一個點數 V2 或券 Job，要求的 `EventSource=OrderPlaced`。分派本身**尚未扣額度**
2. Job 取得同一筆 `PromotionRuleRecord`，做通路檢查和回饋試算。在 DDB key 上取鎖；沒有既有紀錄、`IsMatch=true` 才向 PCPS 呼叫 `dispatch-and-redeem`。回傳 `State=Redeemed` 才當作成功；配額不足則記為失敗。之後寫入 DDB 主／子單。既有紀錄則直接返回，以 DDB 作為重跑的防護之一
3. `OrderCreated` 進入另一個分派器。對有 `GroupCode` 的活動，它把回饋 Job 的 `BookingTime` 設成 `UtcNow + 5 分 10 秒`，試圖讓佔額流程先完成。回饋 Job 若查不到線上佔額活動的 DDB 紀錄，會拋錯而不直接給點／券；查到 `Occupy` 才建立績效 Job 並轉 `WaitToReward`。到真正回饋時間前不執行給點／券

## 為什麼要有獨立的 `Occupy` 狀態？

線上訂單收到 `OrderPlaced` 時，訂單已成立但尚未付款。此時先替符合活動條件的訂單保留額度，並把 DDB 主單記為 `Occupy`。它表達的是「PCPS 已成功佔額，付款結果仍待確認」，因此不會把這筆紀錄直接當成可以給點或給券的 `WaitToReward`。程式中的 `RewardStatusEnum.Occupy` 也明確註明這是訂單成立但未付款的暫時狀態

獨立狀態讓後續流程有清楚的分流依據

1. **付款完成後才進入待回饋。** 回饋 Job 讀到 `Occupy`，才將主單改為 `WaitToReward`，再依回饋時間執行給點或給券。佔額成功本身不等於獎勵已可發放
2. **付款失敗時能精準返還。** `OrderFailed` 只對 `Occupy` 執行 PCPS 返還並更新為 `Cancel`；`Unmatch`、`MatchWithoutQuota`、`Cancel` 都不需要返還。這避免把「有中活動但沒佔到額度」誤當成已佔額
3. **能辨認卡住的中間階段。** 稽核會檢查 `Occupy` 是否仍對應一筆 PCPS 佔額，也會指出訂單已非待付款、DDB 卻仍停在 `Occupy` 的情況，方便追查後續回饋 Job 是否漏執行

線上正向分派器先找待稽核訂單，再依訂單時間區間找回饋活動並建立逐筆稽核 Task。線下批次分派器會另建線下正向與逆流程稽核 Task，`BookingTime` 分別設為建立當下加 **6 小時 30 分**及 **10 小時**；這是排程稽核，不是每次 `dispatch-and-redeem` 成功就立即稽核

**正向佔額筆數規則。** `PromotionRewardQuotaAuditor` 只對規則有 `GroupCode` 的活動檢查。它按訂單來源決定 TG：線上用原 TG，線下加 `CrmSalesOrderCodePrefix`；再用 `ShopId`、會員、`GroupCode`、TG 呼叫 `CheckOrderOccupiedQuota`。該方法以 PCPS `get-by-label` 的回傳筆數計算，查無資料回 `0`

| DDB 主單狀態 | 預期 PCPS 佔額筆數 |
|---|---:|
| `Occupy`、`WaitToReward` | 恰好 1 筆 |
| `Reward`，點數尚未全回收；或券回饋 | 恰好 1 筆 |
| `Reward`，點數已全回收 | 0 筆 |
| `Unmatch`、`MatchWithoutQuota`、`Cancel` | 0 筆 |

超出預期時，Auditor 會回報活動 ID、DDB 狀態、實際筆數與 `groupId`。這裡是計算 `get-by-label` 的查詢結果，**沒有在 Auditor 內逐筆驗證 Code 的 `State`**；查詢的 `Limit` 設為 30

**同一批正向稽核中的其他檢查。** 點數與券的紀錄 Auditor 都會指出「訂單已取消、失敗、出貨或完成，DDB 主單卻仍是 `Occupy`」；券還檢查 `Occupy` 時非 `NoReward` 子單是否為 `WaitToReward`。點數對線上佔額活動另查 DDB 回饋歷程是否出現過 `Occupy`，攤提舊版則跳過歷程檢查。`PromotionRewardPerformanceAuditor` 檢查應有的績效紀錄：`WaitToReward`、`Reward` 及曾經付款後才 `Cancel` 的紀錄須有績效；付款前 `Occupy → Cancel` 不要求績效

**逆流程的返還檢查。** 點數回收稽核在「線上訂單子單全數取消」時查 PCPS 是否仍有佔額，也會對 DDB `Cancel` 或 `Reward` 且點數全回收檢查是否仍有佔額；券回收稽核則對 DDB `Cancel` 檢查。這兩個 Auditor 都略過 `Unmatch`、`MatchWithoutQuota` 和沒有 `GroupCode` 的活動。若查到殘留佔額，會提示確認逆流程 Job 的返還是否完成。

排查一筆訂單時，可固定 `ShopId + PromotionEngineId + TG + MemberId`，依序核對活動 `GroupCode`、正向與逆流程 Job、DDB 狀態及歷程、PCPS 的 Code 筆數與 `CodeId`，再看績效 Job 是否應已建立。DDB 的 `Occupy` 代表系統記錄已佔額，實際是否仍占用額度仍須以 PCPS 查詢結果核對。
